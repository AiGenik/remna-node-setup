# Эксплуатация

## Диагностика

```bash
sudo remna-node-setup status
sudo remna-node-setup doctor
sudo remna-node-setup preflight
sudo remna-node-setup dns node.example.com
sudo remna-node-setup logs
```

Диагностика сверяет постоянные слушающие сокеты Xray с локальными правилами UFW (игнорируя временные эфемерные исходящие UDP-сокеты), проверяет автозапуск `ufw.service` и `ENABLED=yes` в `/etc/ufw/ufw.conf`, синхронизацию времени NTP, состояние IPv6 (`sudo remna-node-setup ipv6 status|disable|enable`) и расписание автоматических обновлений Ubuntu. Если хостинг блокирует `ntp.ubuntu.com`, мастер при настройке или восстановлении автозапуска добавляет резервные NTP-серверы (`time.cloudflare.com`, `time.google.com`) в `/etc/systemd/timesyncd.conf.d/90-remna-ntp.conf`. Доступ с клиентской сети проверяется отдельным подключением.

Если Xray слушает `9443/tcp`, выберите «Порты и защита → Входящие порты и защита SSH» и добавьте `9443/tcp`. Укажите тот же порт в Host. После сохранения подтвердите доступ SSH.

Если диагностика показывает, что автозапуск UFW заблокирован или отключён, откройте **Порты и защита → Восстановить автозапуск защиты**. Мастер включит запуск UFW и установленных служб защиты при загрузке. Подтвердите доступ по SSH.

Проверка DNS показывает отсутствующую запись, ошибку резолвера или расхождение между A/AAAA и адресами VPS. При ошибке установки мастер показывает последние строки вывода операции перед восстановлением снимка.

Для смены веб-сервера откройте «Порты и защита → Self-steal · Caddy или Nginx». Если мастер менял правило UFW для HTTP-01, подтвердите доступ SSH. При ошибке возвращается предыдущая конфигурация. В профиле панели используется `127.0.0.1:8443`.

Журнал сертификатов Caddy доступен через `sudo journalctl -u caddy -n 50`. Для Nginx проверьте `sudo journalctl -u remna-node-setup-certbot.service -n 50` и журналы в `/var/lib/remna-node-setup/nginx-certbot/logs`.

Если BBR выведен как недоступный, VPS использует ядро без нужного алгоритма или не разрешает загрузить модуль. Другие компоненты продолжают работать. `fq` задаётся как очередь по умолчанию для новых интерфейсов.

### Проверка связи до установки

В общей установке проверка идёт после выбора портов и до запуска установки. Отдельно она открывается в «Диагностика → Проверить связь до установки» или через `sudo remna-node-setup preflight`. Сверьте `NODE_PORT` с карточкой ноды и укажите порты VPN из профиля. Для новой ноды отдельная проверка предлагает `443/tcp` и `9443/tcp`. Для `8443/tcp` self-steal и UDP проверяется локальная занятость.

Установите `remna-ssh` на компьютере. Запустите его с `--panel` и укажите SSH-адрес или алиас панели, затем SSH-адрес ноды. Панель должна открываться по SSH-ключу. Помощник запускает тест с панели на адрес ноды из команды или SSH-конфига. Для готовой ноды проверяется обмен TLS, для свободных TCP-портов — передача данных в обе стороны. [Команда запуска](../README.md#помощник-remna-ssh)

При обычном запуске через SSH мастер предложит показать команду для ручной проверки. Enter пропускает внешний тест. Для ручной проверки ответьте `y`, оставьте мастер открытым и вставьте команду в терминал панели. Свободные TCP-порты принимают тестовые данные от указанных IP панели. Сокеты закрываются после проверки. Правила UFW и firewall провайдера действуют во время теста.

Успешный обмен подтверждает TCP с сервера панели при текущих сетевых правилах. Конфигурация Remnawave, ключ, клиентский доступ и выпуск сертификата проверяются после установки.

## Смена порта VPN

1. В меню выберите **[3] Порты и защита → [7] Сменить порт VPN → Подготовить новый порт**. Укажите старый и новый TCP-порты. Мастер откроет новый в UFW и сохранит старый. Подтвердите доступ по SSH. Если у провайдера есть внешний firewall, откройте новый порт и в нём.
2. В панели Remnawave откройте **Config Profiles → профиль ноды → inbounds**. Измените `port` нужного inbound. Для параллельной работы создайте второй inbound с уникальным тегом, назначьте его ноде и добавьте отдельный Host. Если профиль общий, проверьте, какие ноды используют этот inbound. Служебный порт в карточке ноды остаётся прежним. [Config Profiles](https://docs.rw/learn-en/config-profiles/) · [Порт Host](https://docs.rw/learn-en/hosts/#specify-a-port)
3. В **Hosts** укажите новый порт, обновите подписку и подключитесь тестовым VPN-клиентом. Затем снова откройте **[3] → [7]** и завершите перенос. Мастер проверит Xray и UFW на новом порту и обновит перенаправление self-steal, если переносится его порт.
4. Выберите, закрыть старый порт сейчас или сохранить его в UFW. Закрытие доступно после остановки старого inbound. Позже его можно закрыть через **[3] → [7] → Закрыть неиспользуемый**. Мастер блокирует новые TCP-соединения на этом порту. Правила SSH, панели и других VPN-портов сохраняются.

Чтобы отменить подготовку, верните старый порт в профиле и Host, затем выберите **Отменить** в меню переноса. Подтверждение SSH и снимки относятся к настройкам VPS. Изменения в панели и firewall провайдера отменяются там же, где были внесены.

Если профиль сохранён в файл, мастер может заменить один порт в его JSON. Выполните на VPS, затем вставьте содержимое обновлённого файла в редактор профиля.

```bash
umask 077
sudo remna-node-setup vpn-port profile 9443 443 < profile.json > profile-new.json
```

## Подтверждение SSH

После изменения сетевых правил мастер ждёт проверки через отдельное новое SSH-соединение. Если подтверждение не пришло, таймер systemd запускает откат. На экране указано, сколько времени осталось до отката.

Установите `remna-ssh` на свой Mac или Linux и откройте меню с компьютера. [Установка помощника](../README.md#помощник-remna-ssh)

```bash
~/.local/bin/remna-ssh root@203.0.113.10
```

Для другого SSH-порта укажите `--port`, например `~/.local/bin/remna-ssh --port 2202 root@203.0.113.10`. Можно использовать алиас из `~/.ssh/config`. После сетевой операции нажмите Enter. Помощник инициирует новое SSH-соединение, подтвердит операцию и откроет меню снова. При парольном входе SSH может запросить пароль ещё раз.

При ручном запуске оставьте исходный сеанс открытым. Подключитесь к VPS заново без переиспользования ControlMaster и выполните `sudo remna-node-setup confirm` либо выберите **Снимки и восстановление → Подтвердить сетевые настройки**. Если доступ с компьютера потерян, из консоли провайдера можно запустить откат.

## Обновление

В меню «Обновления → Обновить всё» мастер проверяет скрипт и обновляет установленные компоненты. Это включает пакеты, ноду, базу TrafficGuard и управляемый Psiphon. Для сетевых изменений достаточно одного подтверждения SSH.

```bash
sudo remna-node-setup update all
```

### Автообновления

Откройте «Обновления → Автообновления» и подтвердите включение. Проверка запускается ежедневно около 04:00 по времени VPS. Службы могут перезапускаться.

Пакеты, затрагивающие firewall, проходят через ручное «Обновить всё». Фоновое обновление TrafficGuard меняет базу при наличии сохранённого доверенного IP SSH и проверяет общие правила firewall. Если проверка не проходит, мастер восстанавливает снимок.

```bash
sudo remna-node-setup auto-updates status
sudo journalctl -u remna-node-setup-auto-update.service -n 60
```

### Обновление по частям

1. Сохраните снимок в меню или запустите `sudo remna-node-setup backup`.
2. Установите новый стабильный релиз скрипта через «Обновить скрипт» и заново откройте меню.
3. Для Nginx, Caddy, Certbot, UFW, Fail2Ban и Docker выберите «Обновить системные пакеты». Мастер обновит индексы APT и покажет версии установленных пакетов и доступные обновления. Изменения применяются после подтверждения. При обновлении службы могут перезапуститься.
4. Выберите «Обновить TrafficGuard», чтобы скачать текущий стабильный релиз и список сканеров. После применения подтвердите доступ SSH.
5. Сначала обновите панель Remnawave. Затем выберите «Обновить ноду», чтобы скачать свежий стабильный образ. Замена контейнера может прервать соединения. [Порядок обновления Remnawave](https://docs.rw/install/upgrading/)

Для обновления конкретного пакета выполните, например, `sudo remna-node-setup update packages nginx`. APT сохраняет существующие конфигурационные файлы. Пакеты с `apt-mark hold` пропускаются с сообщением. После обновления активный Nginx проходит проверку конфигурации и перезапускается. [Исправления для Nginx в Ubuntu 24.04](https://ubuntu.com/security/notices/USN-9182-1)

В режиме `--local` репозиторий для обновлений задаётся при первом запуске GitHub-установщика с `OWNER/REPO`. `rollback tool` переключает только версию команды. Для возврата конфигурации компонентов восстановите снимок.

## Восстановление

Команда `sudo remna-node-setup rollback` отменяет текущее неподтверждённое сетевое изменение. Красное предупреждение показывает время до автоотката при открытии экрана. Таймер запускается на 10 минут с начала изменения. Если сервер перезагрузится до подтверждения, отсчёт начнётся заново.

Сохранённые снимки находятся в `/var/backups/remna-node-setup`. Выберите «Восстановить снимок» в меню или выполните `sudo remna-node-setup restore ID`. Снимки содержат секрет ноды и доступны root. При восстановлении сетевых правил снова потребуется подтверждение SSH. Установленные пакеты, скачанные образы и данные сертификатов остаются на VPS.

Если не удаётся войти по SSH, используйте консоль провайдера: `sudo remna-node-setup rollback`. Состояние таймера видно через `systemctl status remna-node-setup-rollback.timer`, журнал через `journalctl -u remna-node-setup-rollback.service`.
